# TrustForge Factory

## Purpose

TrustForge is a reusable software factory for building, attacking, verifying, repairing and producing evidence for critical software behavior.

The factory is domain-agnostic. A task supplies the domain specification; the seats supply the engineering process.

## Factory contract

For every stage, the factory follows:

1. Understand the supplied specification.
2. Decompose the work into bounded implementation tasks.
3. Implement only assigned scope.
4. Produce executable validation and evidence.
5. Generate adversarial scenarios against critical properties.
6. Independently verify the implementation.
7. Repair only when a verifier identifies a concrete failure.
8. Re-verify the repair.
9. Preserve the complete evidence chain.
10. Produce a final trust report with explicit limitations.

No seat may self-certify its own work.

## Seat topology

The intended production band has six seats:

- Architect — specification, decomposition, risks and acceptance.
- Builder — scoped implementation and validation.
- Adversary — failure-oriented scenario generation.
- Verifier — independent execution and verdicts.
- Repairer — root-cause analysis and focused repair.
- Evidence — provenance, evidence integrity and final report.

At least three distinct coding-agent seats are required by the event. Six are recommended because the work naturally separates into independent responsibilities.

Each seat must have its own Band Desktop identity, a mandate file, and recorded harness and model.

## Handoff protocol

Every handoff identifies:

- work item;
- objective;
- inputs;
- expected outputs;
- acceptance criteria;
- validation performed;
- observed results;
- evidence references;
- known limitations;
- unresolved risks;
- next owner.

A handoff without executable evidence is incomplete.

## Trust states

- VERIFIED — the stated property was independently verified within the declared scope.
- PARTIALLY_VERIFIED — some required evidence exists, but coverage is incomplete.
- FAILED — a required property was violated.
- INCONCLUSIVE — execution or evidence was insufficient to establish a verdict.
- BLOCKED — required work could not proceed because a dependency or decision is unresolved.

The factory never converts INCONCLUSIVE or BLOCKED into PASS.

## Independence rule

Builder output is evidence for the Verifier, not a verdict.

The Verifier should inspect and execute through the observable product surface whenever possible. Source inspection alone cannot establish runtime correctness.

The Repairer cannot issue a verification verdict. After every repair, work returns to the Verifier.

## Adversarial loop

The Adversary challenges assumptions around retries, duplicate requests, concurrent operations, partial failures, malformed or boundary inputs, authorization boundaries, state persistence and restoration, history and evidence integrity.

Exact scenarios are supplied by the Architect from the current specification. Mandates do not hard-code domain-specific cases.

## Evidence chain

Requirement → Property → Scenario → Implementation revision → Execution → Observation → Verifier conclusion → Repair → Re-verification.

Evidence records preserve provenance and are never fabricated.

## Autonomy mode

During a judged run, the human provides the stage task/specification and then does not steer, approve, debug, or rerun the band until the run completes.

Development-time checks may be used while constructing the factory. They are not substitutes for the autonomous judged run.

## Submission discipline

The factory repository and generated result repository are conceptually separate:

- Factory inputs and mandates define how the band works.
- The result repository contains stage code generated by the band.
- The complete Band room session is preserved as room.json in the submitted result.
- Stage code intended for the judged submission must be produced through the Band collaboration, not manually transplanted into the final stage.

Do not rewrite or squash collaboration history.

## Setup

A production room provides each seat the same absolute result-repository path and the specification for the current stage.

The coordinator dispatches one stage at a time, preserves the previous stage as the baseline for the next, and requires a committed revision before accepting a handoff.

## Cost and timing log

For the final submission, record measured elapsed time per stage, model/harness used by each seat, meaningful retry/repair count, model spend when available, and failed attempts that materially changed the implementation.

Do not invent measurements. Record actual values from room/run history.
